# Тест-план и отчёт по результатам тестирования

## Подход

Тестирование проводится методом чёрного ящика: тесты обращаются к приложению исключительно через публичный HTTP-эндпоинт `POST /endpoint`, без доступа к внутреннему коду или состоянию приложения.

Внешний сервис, от которого зависит приложение (`/auth`, `/doAction`), заменён на WireMock. Это позволяет контролируемо воспроизводить как успешные, так и ошибочные ответы внешнего сервиса, не завися от реальной внешней системы и её доступности.

Каждый тест полностью независим: генерирует собственный уникальный токен и не полагается на состояние, оставшееся от других тестов или от предыдущих запусков всего набора.

## Покрытые сценарии

### LOGIN
- Успешный логин — `200`, `result: OK`
- Повторный логин уже залогиненным токеном — `409`
- LOGIN при недоступности/ошибке внешнего сервиса `/auth` — `500`

### ACTION
- Успешное действие после LOGIN — `200`, `result: OK`
- Действие без предварительного LOGIN — `403`
- ACTION при ошибке внешнего сервиса `/doAction` — `500`

### LOGOUT
- Успешный логаут — `200`, `result: OK`
- Токен становится недействителен после логаута — повторный ACTION с этим токеном возвращает `403`

### Конкуррентный доступ
- При одновременном запросе LOGIN с одинаковым токеном успеть залогиниться должен только один
- При одновременном запросе LOGOUT должен вернутся только один `200`
### Валидация запроса
- Отсутствующий заголовок `X-Api-Key` — `401`
- Невалидный `X-Api-Key` — `401`
- Токен не соответствует формату `^[0-9A-F]{32}$` — `400`
- Отсутствующий параметр `token` — `400`
- Отсутствующий параметр `action` — `400`
- Невалидное значение `action` — `400`

## Особенности поведения, обнаруженные в процессе тестирования

При тестировании выявлено  расхождение между README тестируемого приложения и его фактическим поведением:

 **Формат токена.** В README заявлено "32 символа A-Z0-9". По факту приложение принимает только hex-символы (`^[0-9A-F]{32}$}`) — буквы за пределами `A-F` (например, `G`, `Z`) отклоняются как невалидные.

## Что сознательно не покрыто

- **CI-пайплайн.** Тесты обращаются к живому инстансу приложения, которое по условиям задания не публикуется вместе с тестовым кодом. CI-окружение физически не имеет доступа к артефакту приложения и не сможет запустить его — поэтому настройка CI для этого репозитория была сознательно пропущена, а не забыта.
- Нагрузочное и производительное тестирование — вне рамок задания.
